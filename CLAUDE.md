# COC Data Viewer Development Rules

Read docs/REQUIREMENTS.md before making architectural decisions.

## Project

This is an offline/local-first vehicle data analysis web application
for the COC Formula Student vehicle.

The input is the binary `.log` file generated by the existing ESP32 firmware.

The firmware protocol definition in:
reference/protocol.h

is the authoritative source of truth for binary parsing.

CAN definitions in:
reference/CAN_SIGNALS_SELECTED.md

should be used when decoding vehicle CAN signals.

## Important Rules

1. Do not modify files inside reference/.
2. Do not invent binary protocol fields not present in protocol.h.
3. Do not assume CAN signals that are not documented.
4. If information needed for decoding is missing, explicitly tell the user.
5. Keep the architecture simple.
6. Do not add backend/server/database/authentication.
7. Do not implement features outside V1 unless explicitly requested.
8. Use TypeScript strict typing.
9. Separate binary parsing logic from React UI.
10. Calculation logic must be separated from visualization components.
11. Avoid giant components.
12. Do not optimize prematurely.

## Architecture

Keep these concerns separated:

- parser: binary .log parsing
- decoder: CAN/raw signal decoding
- calculations: derived vehicle values
- UI/components: visualization
- pages: user-facing screens

## Development Process

Before implementing a large feature:
1. inspect relevant existing files
2. explain the proposed change briefly
3. implement the smallest working version
4. run typecheck/build/tests
5. report changed files and remaining uncertainty

Never rewrite large parts of the application unless necessary.

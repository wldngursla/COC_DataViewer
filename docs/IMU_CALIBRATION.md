# IMU calibration and vehicle coordinates

## Unit conversion audit

The parser and `reference/` are unchanged. Sensor values are signed int16, little-endian in 24-byte LOG records, with accel XYZ, temperature, then gyro XYZ. The firmware combines the sensor's big-endian register pairs into signed int16 before writing the little-endian ESP32 struct. The viewer must not swap the bytes again or reinterpret negative counts as unsigned.

The supplied `COC_DataLogger-main (1).zip` firmware `device/firmware/main/peripheral/gyroscope.c` checks WHO_AM_I=0x70 (MPU-6500), then writes GYRO_CONFIG=0x08 and ACCEL_CONFIG=0x10: ±500 deg/s and ±8g. Existing `raw/65.5` and `raw/4096` are correct for these settings. Manufacturer [MPU-6500 Product Specification PS-MPU-6500A-01, tables 1–2](https://uploadcdn.oneyac.com/attachments/files/brand_pdf/invensense_tdk/4E/2C/mpu-6500-datasheet2.pdf) gives 65.5 LSB/(deg/s), 4,096 LSB/g and 16-bit two's-complement output. [TDK's product page](https://www.invensense.tdk.com/en-us/products/inertial-sensors/mpu-6500) also documents the selectable ranges. The BOOT protocol does not record model/configuration registers, so this source inspection does not prove the build/chip used for every historical file. Temperature remains raw; no new temperature conversion is introduced.

Firmware nominally polls/logs at 10 ms (100 Hz), but this is a task cadence, not proof of sensor internal output rate. It also performs a 32-sample gyro hardware-offset calibration at connect/reconnect, assuming a stationary sensor. Software therefore estimates the **residual** bias present in the saved data; it does not subtract the firmware's old offset again. No unit-conversion defect was found and no decoder or firmware formula was changed.

## Data and processing stages

`imuCalibration.ts`, `imuMath.ts` and `imuGForce.ts` are pure calculations. Input ParsedLog columnar arrays remain immutable; parser is not rerun. Processing runs in a worker and is shared between the IMU lab and G-force meters. Excel runs the identical function using a snapshot of the same session settings. New row arrays contain derived data, never replacements for raw counts.

1. **Raw sensor specific force / angular rate**: existing decoded g and deg/s. Preserve signed values, original timestamps and record identity. Flag non-finite data, int16 rails/near rails, configurable axis limits (default 7.9g, 490deg/s), original duplicate/regressing timestamps and sensor error intervals. Sort derived samples by time; mark >500 ms gaps and reset filters.
2. **Stationary calibration**: search the first 120 s of each reconnect epoch in 0.5 s increments for approximately 3 s of continuous stable IMU data. Require at least 30 samples, >=90% duration coverage, no physical errors, one epoch, gaps <=500 ms, acceleration vector standard deviation <=0.035g, gyro vector standard deviation <=0.7deg/s, gravity magnitude 0.8–1.2g and gyro median norm <=5deg/s. At least 80% bounded-nearest GPS matches must exist and all matched speeds must be <1km/h. The component medians estimate residual gyro bias and gravity reference. These are heuristics supported by two signals, not proof of perfect stationarity. Constant-velocity motion cannot be distinguished from rest using IMU alone. With absent GPS, auto calibration is withheld; manual start/end requires the user's explicit stationary confirmation and still passes stability checks.
3. **Mounting rotation**: rows of R_vehicle_sensor are unit vehicle axes expressed in sensor coordinates; output = R*sensor. +X forward, +Y left, +Z up, X×Y=Z. Z comes from normalized stationary specific force under the initial approximately-level-road assumption. One pose cannot distinguish sensor mounting tilt from road/body inclination, accelerometer bias or scale. Forward horizontal direction comes from covariance of projected IMU acceleration and signed GPS speed derivative in straight, sustained acceleration/deceleration. No acceleration scale is invented. Y=Z×X. Every applied R is checked for orthogonality and determinant +1.
4. **Bias-corrected sensor gyro**: subtract only a confirmed bias for that reconnect epoch. A reconnect invalidates the preceding bias; a new stable stop is required. Automatic mounting also rejects an epoch whose stationary gravity direction differs from the initial reference by >5°, because sensor relocation/body inclination is ambiguous. Manual mounting is explicit user input. Sensor-frame filtered acceleration remains available even when vehicle axes are withheld.
5. **Calibrated vehicle specific force / angular rate**: rotate original valid sensor acceleration, and rotate bias-corrected gyro. A lack of stationary calibration does not erase a manually specified rotation's specific-force output, but gyro bias and gravity-derived outputs remain unavailable.
6. **Filtered vehicle values**: sensor-domain centered Hampel (window 7, threshold 3*1.4826*MAD, 0.005 per-component floor, >=5 valid local samples), then optional causal EMA with actual dt and tau=0.15 s. Rotate this processed stream using the same R. An isolated spike bracketed by two unflagged valid neighbors can be interpolated at its actual timestamp; consecutive/unbracketed spikes become null. Range failures are never interpolated. Sustained maneuvers are retained by the median window. This Hampel stage uses future samples (offline); EMA is causal with phase lag, **not** a zero-phase filter. Windows/tau/threshold and physical limits are editable. No Butterworth/zero-phase mode is claimed.
7. **Gravity-compensated acceleration**: specific force and linear acceleration are distinct columns/plots. Subtract a **unit 1g** gravity direction from the appropriate vehicle specific force. Stationary magnitude error is retained; the entire measured 3-vector is not treated as an arbitrary accelerometer bias. The default complementary mode propagates the body components of world up with `dg/dt=-omega×g` using corrected gyro and actual dt. It corrects toward accelerometer direction only during quiet GPS stops; after a gap it needs a confirmed calibration window or a sustained quiet stop. Default correction tau=2 s; without a quiet correction for 30 s the estimate becomes unavailable. This conservative timeout is configurable and is not an accuracy guarantee. Static initial-gravity mode is also available and flags its pitch/roll limitation. Neither mode integrates/export positions, velocities or absolute yaw.

For precise accelerometer calibration, use surveyed six-face static measurements to identify bias/scale, then verify physical mounting. Gravity alone cannot supply yaw. Without an absolute heading reference, gyro drift remains unobservable; constant acceleration can be confused with tilt, so moving accelerometer values are not forced into a gravity estimate. Static mode cannot follow pitch/roll. Specific-force/linear outputs in vehicle coordinates are not Earth-frame coordinates.

## GPS reference, axis estimation and safeguards

The bounded-nearest binary-search alignment from rear-wheel calibration is reused; default tolerance 250 ms. Missing samples are not extrapolated. GPS speed uses a local five-point median and local least-squares slope over at most ±5 samples; actual time is used. Windows need >=5 samples and >=0.4 s span, valid coordinates/directions/course, positive cadence, no gap >500 ms, derivative <=6m/s² and yaw <=90deg/s. GPS speed cap is an analysis heuristic (160km/h). Course changes >30° per record are rejected. Course uses shortest-difference unwrap through 0°/360°; course is unobservable below 8km/h.

NMEA course increases clockwise from north. Vehicle +Z yaw is left-turn-positive, so **GPS yaw = -d(course)/dt**. GPS lateral acceleration = speed(m/s)*yaw(rad/s)/9.80665 in g. These remain independent comparison signals and never overwrite IMU values. GPS fix/HDOP/satellite quality is not in this protocol and cannot be certified.

Lag estimation uses only the first 70% of the GPS timeline and signed gyro projected on the gravity-derived up vector. Search ±1.5 s in 100 ms steps, >=30 matches, variance >=4(deg/s)² in both signals, correlation >=0.75, non-boundary maximum and >=0.02 advantage over alternatives >=500 ms away. Ambiguous lag is withheld to zero; manual lag ±5 s is supported. Positive lag compares IMU(t) with GPS(t+lag). Since IMU references may be filtered, this is an effective alignment estimate, not a measured hardware latency.

Forward candidates require >=8km/h, |GPS acceleration| 0.3–3m/s² with the same sign about 0.4 s earlier, |GPS yaw|<=3deg/s and |bias-corrected gyro-up|<=5deg/s. Available rear-wheel speeds must each agree with GPS within max(5km/h,25%) to exclude obvious disagreement/possible slip. Missing wheels do not prove no slip. The final 30% is reserved for independent validation. Automatic axes require >=40 training and >=20 validation points, acceleration **and** deceleration of at least 0.04g in each partition, forward validation R²>=0.5 and RMSE<=0.08g, plus >=30 held-out turn samples, gyro-up yaw MAE<=5deg/s and R²>=0.5. Thresholds are conservative heuristics, not calibration certificates. Rejected-candidate counts, candidate matrix and validation metrics are visible.

GPS course is travel direction, not body heading. Even excellent scalar-speed correlation cannot resolve forward-versus-reverse body heading on its own. The user must confirm that calibration segments represent **forward driving**, or enter mounting directly. Without adequate data/confirmation, vehicle axes and vehicle G-force stay N/A. Manual mappings accept signed permutations only when right-handed; manual angles explicitly use `Rz(yaw)*Ry(pitch)*Rx(roll)` as the sensor→vehicle rotation. Manual input is not labeled automatically validated.

## UI / Excel

Graphs → **IMU Calibration · Vehicle Coordinates** provides Raw / Calibrated / Filtered / Compare, specific-force versus linear view, independent GPS longitudinal/yaw/lateral lines, calibration interval/bias/gravity, applied and candidate rotations, lag, holdout errors, cadence and quality counts. When mounting is withheld, filtered **sensor** specific force and confirmed sensor gyro bias correction remain available and are explicitly labeled as sensor axes. Vehicle-frame values remain null. Existing legacy raw sensor graphs/maps/replay remain available.

G-force meters use the shared vehicle **filtered linear** output. Up is +X acceleration, down is braking; left is +Y left-turn acceleration. There is a clearly labeled sensor Raw mode with gravity included. Invalid/latest rows cannot resurrect an earlier valid dot. Unknown mounting, missing stationary calibration, disabled gravity removal or stale gravity yields N/A in vehicle mode. MAX values use only valid samples in the selected mode.

Excel preserves original IMU rows/counts/file order and original raw/decoded columns, then adds named vehicle specific-force, corrected angular-rate, filtered, linear, filtered-linear and estimated-gravity vectors plus GPS references, quality and calibration status. `IMU_Sensor_Processed` supplies sensor gyro residual-bias correction and filtered sensor results. `GPS_IMU_Reference` retains GPS sample timestamps. `GForce_Analysis` matches vehicle meter values, while `GForce_Sensor_Raw` preserves the raw meter view. Summary includes settings, numeric R entries, epoch-specific calibration vectors/intervals, success status, limitations and errors. Null stays blank, zero stays numeric; worksheet splitting behavior is retained. No log is reparsed or uploaded.
